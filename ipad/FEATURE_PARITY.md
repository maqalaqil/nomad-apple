# NOMAD Apple: full feature coverage ledger

Upstream baseline: `Crosstalk-Solutions/project-nomad` commit **54ee30a44902e5c252b477f8685c26ec3064ab72** (v1.35.1 release documentation). This ledger covers that checkout, not an unbounded promise to mirror future upstream additions.

Target: a standalone native application on stock iPadOS 26 or later, with an Apple-silicon iPad as the intended hardware baseline. Storage and memory requirements depend on selected content and models. Every baseline feature below remains in scope; implementation phases describe sequencing, not feature removal. A dashboard tile, placeholder, renamed module, or successful build does not establish feature parity. M1 performance and complete offline acceptance remain unverified.

## Status meanings

- **Partial:** some working source exists, but the complete upstream capability is not implemented or verified.
- **Not implemented:** no corresponding functional engine/workflow is connected yet.
- **Integration required:** depends on an engine, external protocol, dataset, authorized service, or entitlement that is not connected/confirmed.
- **Platform adaptation:** a native equivalent needs explicit changed semantics because stock iPadOS or the hardware cannot provide the same server/platform behavior.
- **Verified:** reserved for a completed acceptance case with recorded evidence. No row starts verified merely because it compiles.

This ledger describes the development preview exported on November 4, 2026. Check counts below are historical results from the development checkout, not a claim that every public checkout has passed a clean build. The public [validation summary](../docs/VALIDATION.md) records their scope; [test instructions](Tests/README.md) explain how to repeat the included harnesses. Private device reports, personal installation details and live download state are not part of this repository. Full feature parity, airplane-mode cold launch, restart acceptance and release distribution remain open gates.

## Non-negotiable platform distinctions

1. **Offline content must already be installed.** New models, archives, courses, maps, app updates, external catalogs and leaderboard submissions cannot become available without a transfer path. After preparation, existing data must continue working without WAN, Wi-Fi or cellular access as appropriate to each module.
2. **Storage is not working memory.** 512 GB determines content capacity, not which language models fit in memory. Test the actual device under pressure. Bound indexing, raster exports and inference; serialize heavy jobs when necessary.
3. **iPadOS controls app lifetime.** Persist work and resume after suspension/termination. Do not promise an always-on Jellyfin/Vaultwarden/Kolibri/Docker server, indefinite background inference, or exact-time unattended jobs.
4. **Native equivalents do not imply protocol/file-format parity.** Name formats and interfaces actually supported. In particular PencilKit is not Excalidraw, Keychain is not a Bitwarden sync server, and AVKit is not a Jellyfin transcoder.
5. **External radios remain physical prerequisites.** Both mesh modules stay in scope, with hardware requirements disclosed. Without accessories, configuration records may be stored, but real LoRa communication is unavailable.
6. **Gated integrations require authorization.** Creator Pack entitlements, upstream benchmark acceptance, content redistribution licenses and third-party engine licenses are release gates, not assumptions.
7. **App installation must remain valid offline.** Choose a supported distribution/signing path and test its actual constraints. A temporary development installation or expiring test build is not a permanent offline appliance guarantee.

## Shared acceptance evidence required before calling a feature complete

- Fresh setup/import followed by force-close/relaunch and device restart.
- Airplane mode with Wi-Fi disabled; core operation uses only local assets and data. Radio features use only their documented optional radio path.
- Genuine user data rather than seeded demonstration entries; empty states are usable.
- Unsupported/corrupt files, insufficient storage and unavailable engines produce visible recoverable errors.
- Delete and replace operations require explicit confirmation; cancel preserves existing data.
- Saved data survives interruptions; failed imports/saves cannot silently overwrite an intact collection.
- Exported/backup data reopens correctly in the intended independent consumer or native restore workflow.
- Model preparation, translation and playback are tested on each supported physical device class. M1 needs its own hardware evidence; simulator availability or a different iPad is not a substitute.

## Validation scope

The [public validation summary](../docs/VALIDATION.md) and [test instructions](Tests/README.md) distinguish portable regressions, native/WebKit engines, simulator UI checks and physical diagnostics. Historical counts are scoped to their named harness; they are not an aggregate coverage percentage or a guarantee for arbitrary content.

Large-file memory regressions exercise the production download verifier, course importer, ZIM resource handler and reference importer with temporary fixtures. They establish bounded streaming behavior under those workloads. Sparse-file size/capacity tests do not validate the real worldwide map or complete Wikipedia content. Short model-generation runs do not establish answer quality, language coverage or sustained performance. Installed-only translation APIs do not establish that models have been prepared, and an online device diagnostic does not establish airplane-mode behavior.

No feature is silently removed when its status remains partial or not implemented. Full feature parity, permanent offline distribution, App Store readiness and end-to-end M1 acceptance are not complete. Dependency licensing and distribution gates are recorded in [DEPENDENCIES.md](DEPENDENCIES.md).
